# Codex参照: LS入力で発生したコンパイルエラー修正の教訓

## 1. 目的
本ドキュメントは、LS入力プロジェクトで実際に発生したコンパイルエラーおよびそれに類する重大な構成ミスを振り返り、別プロジェクトで同様の不具合を再発させないための確認事項を整理したものです。各項目は過去の修正PRを参照しながら、症状・原因・恒久対策の観点でまとめています。

## 2. 修正履歴と再発防止策

### 2.1 PR #77: 統合マスタ読み込みのUDT管理（2025-09-25）
- **症状**: 統合マスタのレコードを `Collection` に格納した状態でユーザー定義型 (`IntegratedMasterRecord`) を扱おうとすると、VBAでは Variant 変換ができずコンパイルが通らない環境がある。特にモジュール構成を整理した後に他ブックへ移植すると、コレクション経由でUDTを扱う処理がビルド時に拒否される。
- **原因**: `Collection.Add` は Variant を要求するが、ユーザー定義型を Variant に格納するには型宣言モジュールの公開条件を満たす必要がある。保守マクロを他フォルダへ移動した際にこの前提が崩れ、`LoadIntegratedMaster`／`MatchSubjectWithMaster` がコンパイルできない状態になった。
- **対策**: レコードを可変長配列と件数カウンタで管理し、`Collection` に依存しない実装へ置き換えた。これによりUDTを Variant に変換せずに安全に取り扱える。【F:LS入力/ModIntegratedMaster.bas†L214-L341】
- **再発防止チェック**:
  - UDTを永続化・集約する場合は `Collection` ではなく配列またはクラスを使用する。
  - モジュールの公開範囲を変更したときは、UDTを受け渡ししているプロシージャのシグネチャを全て再検証する。

### 2.2 PR #75: 共通設定定数の参照漏れ（2025-09-25）
- **症状**: `InitializeTransferConfig` で `DEFAULT_COLUMN_ADD_POLICY` 等の共通定数を参照する際にモジュール名を付けずに使用していたため、別モジュールへ移管した時点でコンパイル時に「変数が定義されていません」となる。
- **原因**: 定数を `ModAppConfig` に移動したが、呼び出し側でモジュール修飾子を付与しておらず、`Option Explicit` の下で未定義扱いになった。
- **対策**: 共有定数を `ModAppConfig` に集約し、呼び出し側では必ず `ModAppConfig.DEFAULT_DRY_RUN_MODE` のようにモジュール名を明示する運用へ統一した。【F:LS入力/ModAppConfig.bas†L12-L24】【F:LS入力/ModDataTransfer.bas†L350-L353】
- **再発防止チェック**:
  - 共通設定を別モジュールへ移す際は参照元の全検索 (`rg`) を行い、モジュール修飾子を付け忘れていないか確認する。
  - Lint 相当のテスト（全モジュールのコンパイル）をCIの代替として常に実施する。

### 2.3 PR #67: Enum型定数の型宣言ミス（2025-09-18）
- **症状**: `Private Const AUTO_ADD_POLICY As ColumnAddPolicy = AddPolicy_Prompt` のように Enum 型で `Const` を宣言すると、「定数式が必要です」とコンパイルエラーになる環境がある。
- **原因**: VBAでは `Const` に Enum 型を直接指定できず、内部的には Long に暗黙変換して保持する必要がある。
- **対策**: 列追加ポリシーの既定値を `ModAppConfig` 側で `Long` 定数として定義し、転記処理側では `Long` として受け取るようにした。【F:LS入力/ModAppConfig.bas†L19-L24】【F:LS入力/ModDataTransfer.bas†L120-L123】
- **再発防止チェック**:
  - Enum を初期値に使う場合は `Const` ではなく `Public Enum`＋`Long` 定数の組み合わせにする。
  - プロジェクトのOption設定が異なる環境（32bit/64bit）でもコンパイルできるか確認する。

### 2.4 PR #66: `ChrW` を含む定数式の誤用（2025-09-18）
- **症状**: `Private Const WORK_KEY_DELIMITER As String = ChrW(&H1F)` のように関数呼び出しを含む `Const` 宣言が「定数式が必要です」でコンパイルエラーになる。
- **原因**: VBAの `Const` はリテラルか算術演算のみ許容し、`ChrW` のような関数は使用できない。
- **対策**: 文字コードは `Long` 定数として保持し、使用時に専用の関数で `ChrW$` へ変換するヘルパー関数を用意した。【F:LS入力/ModDataTransfer.bas†L73-L217】
- **再発防止チェック**:
  - Unicode 文字を定数化したい場合は「コードポイントを数値で保持→ヘルパーで文字列化」のパターンに統一する。
  - 既存の `Const` に関数が含まれていないか一括検索する。

### 2.5 PR #31: Type 宣言の位置ずれ（2025-09-01）
- **症状**: ユーザー定義型より前にプロシージャを宣言していたため、「ユーザー定義型が定義されていません」でコンパイルに失敗した。
- **原因**: VBAでは同一モジュール内で `Type` 宣言が一つでもプロシージャの後ろにあると、その `Type` を参照するプロシージャが認識できなくなる。
- **対策**: `WorkKey` などの `Type` 宣言をモジュール冒頭（定数の直後）へ移動し、`RaiseCustomError` などの汎用プロシージャはその後ろへ配置した。【F:LS入力/ModDataTransfer.bas†L104-L133】
- **再発防止チェック**:
  - モジュールを整理するときは「Option Explicit → Const → Type → Enum → Public Sub」の順に並べるルールを徹底する。
  - 新しい `Type` を追加した際は即座にコンパイル（Debug → コンパイル VBAProject）を実行する。

### 2.6 PR #52-53: テスト用エントリーポイントの公開漏れ（2025-09-17）
- **症状**: メンテナンス用テストモジュールからイベントプロシージャ (`Worksheet_BeforeDoubleClick`) を直接呼び出すと、`Cancel` 引数の扱いが複雑になり、他ブックへ移植した際にハンドラ名の不一致や `Option Private Module` 設定による未公開問題でコンパイルが通らないケースがあった。
- **原因**: イベント専用プロシージャは公開されないため、テストコードが別モジュールに移った途端に呼び出し元が解決できなくなった。
- **対策**: イベント本体を `HandleDoubleClickClear` に分離し、テスト用に `RunDoubleClickClear` を公開して、常に公開メソッド経由で呼ぶよう統一した。【F:LS入力/ダブルクリック削除r1.cls†L40-L107】【F:LS入力/maintenance-macros/ModTestRunner.bas†L61-L71】
- **再発防止チェック**:
  - イベントハンドラをテストする場合は、必ず公開メソッドに実装を委譲する。
  - メンテナンス用マクロを別ブックへ移植するときは、参照しているメンバーが `Public` かどうかを確認する。

## 3. まとめチェックリスト
1. **定数宣言**: 関数呼び出しを含めず、Enum 値は `Long` 定数経由で使用する。【F:LS入力/ModDataTransfer.bas†L73-L217】【F:LS入力/ModAppConfig.bas†L12-L24】
2. **ユーザー定義型**: `Type` はモジュール冒頭にまとめ、Collection ではなく配列で管理する。【F:LS入力/ModIntegratedMaster.bas†L214-L341】【F:LS入力/ModDataTransfer.bas†L104-L133】
3. **共通定数の参照**: 共有モジュールの定数は必ずモジュール名を付けて呼び出す。【F:LS入力/ModDataTransfer.bas†L350-L353】
4. **イベントテスト**: イベントロジックを公開メソッドに分離し、テストや他モジュールからは公開メソッドを利用する。【F:LS入力/ダブルクリック削除r1.cls†L40-L107】【F:LS入力/maintenance-macros/ModTestRunner.bas†L61-L71】
5. **コンパイル確認**: モジュールの配置や参照を変更した直後に「コンパイル VBAProject」を実施し、早期にコンパイルエラーを検知する。

本チェックリストを別プロジェクトへ適用することで、LS入力で発生したコンパイルエラーと同種の不具合を未然に防ぐことができます。
