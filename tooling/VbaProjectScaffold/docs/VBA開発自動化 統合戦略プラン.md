# **VBA開発自動化 統合戦略プラン**

## **1\. 目的と背景**

LLM（Codex等）の活用によりVBAコードの生成は高速化したが、それをExcelファイルに組み込み、テストし、配布可能にするまでの一連のプロセスには、依然として多くの手作業が介在している。本プランは、これらの手作業を可能な限り自動化し、開発サイクルを高速化・安定化させるための統合的な戦略を定義するものである。

**対象環境:** Windows 11 / Excel 2016（デスクトップ版）

## **2\. 現状の課題**

3つの資料から共通して抽出された課題は以下の通りである。

* **手動による非効率な作業:**  
  * Excelブックの新規作成やテンプレートの準備  
  * 生成された.bas / .clsファイルのVBE（Visual Basic Editor）への手動インポート  
  * 参照設定（Scripting Runtime等）の手動追加  
  * テストの都度、手動でマクロを実行し、結果を目視で確認  
* **開発サイクルの遅延:** コード修正のたびにインポートとテストを繰り返す必要があり、サイクルが長い。  
* **ヒューマンエラーのリスク:** 繰り返しの手作業は、設定ミスやインポート漏れなどの人為的ミスを誘発する。  
* **セキュリティ設定の障壁:** マクロのセキュリティ設定や「VBAプロジェクト オブジェクト モデルへの信頼を付与（AccessVbom）」が自動化の妨げとなる場合がある。  
* **環境依存の問題:** 参照設定のパスが開発者ごとに異なる、Officeの32/64bit版の違いでコードが動作しない、といった問題が発生しやすい。

## **3\. 自動化のゴール（目指すべき姿）**

* **ワンコマンド実行:** コマンド（またはバッチファイル）を一つ実行するだけで、以下の処理がすべて自動で完了する。  
  1. テンプレートから新しいExcelファイルを生成  
  2. ソース管理下にあるVBAファイル（.bas, .cls）を自動でインポート  
  3. 必要な参照設定を自動で追加・修復  
  4. テストデータを投入し、テスト用マクロを自動実行  
  5. テスト結果をログファイル（CSV, JSON等）に出力  
* **再現性の確保:** いつ、誰が実行しても同じ成果物が生成される状態を保つ。  
* **GUI操作からの脱却:** 可能な限り画面操作に依存しないプロセスを構築し、安定性を向上させる。

## **4.【結論】推奨アーキテクチャ**

各提案を比較検討した結果、以下のハイブリッド構成が最も効果的であると結論付ける。

* **主軸（コアエンジン）: PowerShell \+ Excel COM**  
  * **役割:** Excelアプリケーションを背後で操作する中核。ファイルの生成、VBAのインポート、マクロの実行、保存など、主要な処理を担う。  
  * **選定理由:** GUIに依存せず高速かつ安定している。Windows標準機能であり導入が容易。ログ出力や外部ツールとの連携も柔軟に行えるため、自動化の基盤として最適。  
* **補助（サポートツール）: Power Automate Desktop (PAD) / AutoHotkey**  
  * **役割:** COM操作だけでは困難なUI操作（初回のみ必要なセキュリティセンターの設定変更、参照設定ダイアログの特殊な操作など）を補助的に自動化する。  
  * **選定理由:** あくまで補助的な役割に留めることで、画面解像度やウィンドウの状態に依存するUI自動化の不安定さを最小限に抑える。  
* **実行ランナー: バッチファイル / VSCodeタスク**  
  * **役割:** PowerShellスクリプトやPADのフローを適切な順序で呼び出す「起動スイッチ」。開発者はこれを実行するだけでよい。

## **5\. 実装に向けた段階的ロードマップ**

### **Step 1: 基本的なビルド自動化（MVP: Minimum Viable Product）**

まず、手作業で最も時間のかかる「VBAコードのインポート」を自動化する。

1. **事前準備:**  
   * Excelのセキュリティセンターで「VBAプロジェクト オブジェクト モデルへの信頼を付与」を**開発時のみ有効化**する。（※終了時に元に戻すスクリプトも用意）  
   * ベースとなるテンプレートExcelファイル（.xltmまたは.xlsm）を用意する。  
2. **PowerShellスクリプトの作成:**  
   * テンプレートファイルをコピーして新規ブックを作成する。  
   * 指定したフォルダ内にある.bas / .clsファイルをすべてインポートする。  
   * 必要な参照設定をGUID（Globally Unique Identifier）で追加する。  
   * マクロ有効形式（.xlsm）で保存する。

### **Step 2: テストの自動化と開発環境の整備**

ビルドプロセスにテスト実行を組み込み、開発体験を向上させる。

1. **VBAテストハーネスの作成:**  
   * Excelテンプレート内にTestRunnerといった名前の標準モジュールを作成する。  
   * RunAllTestsのような公開プロシージャを定義し、その中で個別のテストプロシージャ（例: Test\_Case1）を呼び出す作りにする。  
   * テスト結果（成功/失敗/エラー内容）を特定のシートや外部ファイル（CSVなど）に出力する機能を持たせる。  
2. **PowerShellの拡張:**  
   * Step 1のスクリプトに、VBAのRunAllTestsプロシージャを呼び出す処理 ($excel.Run("RunAllTests")) を追加する。  
   * テスト結果ファイルの内容を読み取り、処理の成功/失敗を判断する。  
3. **リポジトリ構成の整備:**  
   * ソースコードや関連ファイルを体系的に管理するためのフォルダ構成を定義する。

project-root/  
  ├─ src/vba/        \# ソース管理する.bas, .clsファイル  
  ├─ template/       \# 元となるExcelテンプレート  
  ├─ tests/          \# テスト用のデータや期待結果ファイル  
  ├─ tools/          \# PowerShellスクリプト等を格納  
  ├─ build/          \# 自動生成された成果物やログを格納  
  └─ config/         \# 参照設定などを記述する設定ファイル (例: manifest.json)

### **Step 3: CI/CDへの拡張**

個人のPCだけでなく、チームでの開発や定期的な自動実行を見据えた仕組みを構築する。

* **ローカルCI (Continuous Integration) の実現:**  
  * Gitでソースコードをpushしたことをトリガーに、WindowsタスクスケジューラやGitフックを利用して、自動でビルドとテストを実行する仕組みを構築する。  
  * これにより、コードの変更が既存の機能に悪影響を与えていないかを常に確認できる。

## **6\. 主要ツール比較と考察**

| ツール | 導入難易度 | 安定性 | 速度 | GUI依存 | 総合評価（本プランでの位置づけ） |
| :---- | :---- | :---- | :---- | :---- | :---- |
| **PowerShell (COM)** | 容易 | ◎ (高い) | ◎ (速い) | 低 | **主軸**。安定性と柔軟性を両立。 |
| **PAD / AutoHotkey** | 容易 | △ (低い) | ○ (普通) | 高 | **補助**。COMで不可能なUI操作に限定。 |
| **Python (pywin32)** | 普通 | ◎ (高い) | ◎ (速い) | 低 | **代替案**。PSと同等だが環境構築が必要。 |
| **VSTO (C\#)** | 難しい | ◎ (高い) | ◎ (速い) | 低 | **将来的な選択肢**。高機能だが開発コスト大。 |

考察:  
PowerShellはWindows環境における自動化の第一選択肢であり、Excel COMとの親和性も極めて高い。Pythonも強力な選択肢だが、実行環境の構築が必要な点を考慮すると、手軽さでPowerShellに軍配が上がる。UIに依存するPADやAutoHotkeyを主軸にすると、メンテナンス性が著しく低下するため、あくまで補助的な「最後の手段」と位置づけるのが賢明である。

## **7\. まとめ**

本プランは、ご提示いただいた3つのアプローチを統合・昇華させた、LLM時代のVBA開発におけるベストプラクティスです。**PowerShellによるバックグラウンド処理**を主軸に据え、段階的に自動化の範囲を広げていくことで、開発者は本来注力すべきロジックの実装に集中できるようになります。

まずは\*\*Step 1の「基本的なビルド自動化」\*\*から着手し、その効果を実感することをお勧めします。
